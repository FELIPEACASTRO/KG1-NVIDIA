## Findings That Survived The Second Pass

### 1. Use hard negatives that match the model's real failure mode

This is the strongest consensus in the file. The rejected response must be exactly the frozen adapter's wrong answer or wrong trace for that row/variant. Random wrong strings create easy pairs and can leave the high-confidence wrong token untouched.

Implementation impact:

- Capture frozen adapter raw outputs for the 4 equation IDs and 11 bit IDs.
- Build chosen/rejected pairs:
  - chosen: verified correct output with compact trace;
  - rejected: frozen adapter output with the observed wrong final answer.
- Reject generic hard-negative generation unless it is verifier-checked and tied to an observed failure mode.

### 2. Weight final answer tokens, not trace boilerplate

Several higher-signal responses describe the same failure: the important answer is often one to three tokens while the trace may be hundreds of tokens. Standard next-token loss can optimize formatting and ignore the final answer.

Implementation impact:

- V317 should use a trainer with answer-span mask.
- Start with moderate multipliers (`3x` to `5x`) before considering extreme `15x`.
- Template should end with a machine-detectable span, for example:

```text
RULE:{rule_id}
CHECK:{minimal guard}
ANSWER:{final_answer}
```

### 3. Treat bit keepers as mandatory, not optional

V313 and V315 both showed bit regression. This is not theoretical. The file's useful advice converges on all currently-correct bit rows being replayed as keepers.

Implementation impact:

- Include all 135 baseline-correct bit rows in training or mandatory validation.
- Keep all 160 bit rows represented in the probe:
  - 135 keeper-correct rows;
  - 11 target-gain rows;
  - 14 non-gain wrong rows as distribution stabilizers.
- If `bit<135`, hard reject. If `bit=135` and equation improves, evaluate cautiously. If `bit>=136`, candidate can promote.

### 4. Use exact IDs as probes, not as the only SFT source

The exact target rows are valuable for gating, but using only those exact rows as SFT targets risks local memorization. Several responses mention variants, contrastive guards, or anti-trigger rows. This is correct, but variants must be generated by deterministic/verifier code, not by model imagination.

Implementation impact:

- Exact IDs:
  - use in probes;
  - use in DPO only if rejected output is frozen-adapter output;
  - avoid relying on them as the full SFT target set.
- SFT rows:
  - generated programmatically from verified rule variants;
  - include counterexamples where the guard fails and the transform must not fire.

### 5. Checkpoint selection must be probe-first

The attachment repeatedly recommends checkpoint gates. That is aligned with our HF process, but V317 should be stricter than V316:

- equation exact probe: `4/4` expected for the direct target;
- bit target probe: at least movement on the 11 IDs before weak/full eval;
- bit keeper probe: no broad loss;
- truncation: no worsening;
- weak gate: prefer `total>=193`, `equation>56`, `bit>=136`.

## Findings Rejected After Second Pass

### High learning rates

Many responses suggest `1e-4`, `1.5e-4`, `3e-5`, `5e-5`, or even higher. The frequency does not make this safe. It conflicts with our successful adapter lineage, where changes around `1e-8` are already meaningful. High LR remains rejected unless a separate low-cost smoke experiment proves it will not destroy the baseline.

### Sequential equation-only training

Some responses suggest equation-first or equation-only phases. Given observed bit regression, this is too risky unless paired with mandatory bit replay and early rollback. The safer version is interleaved training from the start.

### Dual LoRA / router

This may be technically interesting, but it adds artifact complexity. The current goal is a Kaggle-valid LoRA-only behavior, so the next practical step is still single-adapter training with stronger objective shaping.

### KL regularization as first implementation

KL is plausible but adds complexity and cost. The cheaper first defense is explicit bit replay and checkpoint rejection. Add KL only if replay does not stop regressions.
